# ส่วนที่ 1 — บั๊ก "ปิดแจ้งเตือนหนุนดวงแล้วไม่หยุด"

## 🔴 ต้นตอหลัก: การปิดหมดอายุเองใน 7 วัน (ไม่ใช่ 400 วันอย่างที่ตั้งใจ)

`setDailyPickOptout()` ขอ TTL **400 วัน** (`OPTOUT_TTL_SECONDS = 400 * 86400`)
แต่ `setValueWithTtl()` ใน `src/redis/scanV2Redis.js` **cap TTL ไว้ที่ 604,800 วินาที = 7 วัน**:

```js
await r.set(kDedupe(key), String(value).slice(0,200), "EX",
            Math.min(Math.max(Number(ttlSec) || 3600, 60), 604800));  // ← เพดาน 7 วัน
```

→ ลูกค้ากดปิด ระบบตอบ "ปิดให้แล้วครับ" **แต่ 7 วันต่อมาการปิดหายไปเองเงียบ ๆ แล้วแจ้งเตือนกลับมาอีก**

**หลักฐานจากระบบจริง:**
- ลูกค้าที่ได้รับข้อความยืนยัน `replyType=daily_pick_notify_toggle` = **10 คน**
- key `*daily_pick_optout*` ที่เหลืออยู่ใน Redis = **2 key เท่านั้น** และ **TTL เหลือ 1 วัน / 2 วัน** (สอดคล้องกับเพดาน 7 วันเป๊ะ)
- Redis ไม่ได้ restart (uptime 65 วัน) → ไม่ใช่ข้อมูลหาย แต่**หมดอายุตามเพดาน**
- → **อีก 8 คนที่ปิดไปก่อนหน้า การปิดหมดอายุไปแล้ว กำลังได้รับแจ้งเตือนอีกรอบ**

**C. คิวไม่เช็คซ้ำก่อนส่ง**

## แยก "แจ้งเตือนอัตโนมัติ" ออกจาก "รายงานที่ลูกค้าสั่ง" (ตามที่สั่ง)

ตอนนี้ `deliverOutbound` เอา 4 kind มารวมใน branch เดียวกัน: `renewal_reminder`, `daily_pick_push`, `fb_consent_ask`, `scan_failure_notify`
**ต้องแยกให้ชัดว่า optout ปิดอะไรได้บ้าง:**

| kind | ประเภท | optout ควรปิดไหม |
|---|---|---|
| `daily_pick_push` | **แจ้งเตือนแนะนำอัตโนมัติ** (ลูกค้าไม่ได้ขอ) | ✅ ปิดได้ |
| `fb_consent_ask` | ขออนุญาตอัตโนมัติ | ✅ ควรปิดได้ด้วย (แต่คนละสวิตช์) |
| `renewal_reminder` | เตือนต่ออายุ = เกี่ยวกับเงินที่เขาจ่าย | ⚠️ ควรมีสวิตช์แยก ไม่ปิดพร้อมกัน |
| `scan_failure_notify` | **ตอบงานที่ลูกค้าสั่งเอง** (สแกนล้ม) | ❌ **ห้ามปิด** — ไม่งั้นลูกค้าส่งรูปแล้วเงียบหาย |

## Acceptance ก่อนถือว่าแก้จบ

1. ปิดแล้วอยู่ถาวร: ตั้ง optout → ตรวจ TTL ≥ 45 วัน (หรือเก็บใน DB) → จำลองเวลาผ่าน 8 วัน → ยังปิดอยู่
2. คำสั่งไม่ถูก AI แย่ง: ยิง "หยุดแจ้งเตือน" จากทุก conversation state ที่มี orchestrator → ต้องได้ `replyType=daily_pick_notify_toggle` ทุกครั้ง (0 ครั้งที่เป็น `gemini_front_reply`)
3. คิวเคารพการปิด: enqueue แล้วปิดก่อน worker ส่ง → ต้องไม่ส่ง และมี log suppressed
4. ไม่กระทบงานที่ลูกค้าสั่ง: ปิดแจ้งเตือนแล้วสแกนล้ม → **ยังต้องได้รับ** `scan_failure_notify`
5. เปิดกลับได้: "เปิดแจ้งเตือน" → รอบถัดไปได้รับปกติ
6. full gate ไม่มี fail ใหม่ · ไม่แตะ prompt/model

## เยียวยาลูกค้าที่ได้รับผลกระทบ (รอกบเคาะ)

10 คนเคยกดปิด · 8 คนการปิดหมดอายุไปแล้ว → เสนอ: **หลัง patch ให้ตั้ง optout กลับให้ทั้ง 10 คนโดยอัตโนมัติ** (จาก log `daily_pick_notify_toggle` ที่มีบันทึกครบ) เพื่อไม่ให้ต้องกดปิดซ้ำ — เป็นการคืนสิ่งที่เขาเคยขอไว้ ไม่ใช่การเปลี่ยนการตั้งค่าเอง

## สิ่งที่ต้องออกแบบก่อนเขียนโค้ด
