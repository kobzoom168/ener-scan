## 2. E — journald: ระบุอายุเก็บ
- ปัจจุบัน: 3.9G, 102 ไฟล์, เก่าสุด ต.ค. 2025 · ขนาดต่อเดือน: ก.ย. 2026 **2.9G** (ช่วง incident 29 ก.ย.), ต.ค. 1.4G (19 วัน) · ผู้เขียนหลัก 24 ชม.: `sshd` 86,781 บรรทัด (brute force), kernel 18,642, systemd/containerd/dockerd · ข้อความ ~15MB/วัน
- **ข้อเสนอ (แก้ตาม Codex):** จำกัด **พื้นที่** เป็นหลัก `SystemMaxUse=1G` (ไฟล์ `/etc/systemd/journald.conf.d/50-retention.conf`) **โดยยอมให้ประวัติที่เหลือสั้นกว่า 2 เดือน** — ด้วยอัตรา ก.ย. 2.9G/เดือน, ต.ค. 1.4G/19 วัน เพดาน 1G จะเหลือประวัติประมาณ **2–3 สัปดาห์ล่าสุด** ไม่ใช่ 2 เดือน (ไม่รับประกันช่วงเวลา) · `journalctl --vacuum-size=1G` ลบเฉพาะไฟล์ **archived** (system@….journal) ไล่จากเก่าสุดจนยอด archived ≤1G — ไฟล์ active `system.journal` (25MB ตอนนี้) ไม่ถูกนับ/ลบ จึง **ยอดรวมหลัง vacuum ≈ 1G + active ไม่ใช่ 1G พอดี** · `--vacuum-time` ให้ผลต่างกัน (ลบตามอายุไม่สนขนาด) — ใช้อย่างใดอย่างหนึ่งตามที่กบเลือก
- **ช่วงที่จะสูญเสีย (ระบุชัด):** journal ตั้งแต่ ต.ค. 2025 ถึงประมาณ **ปลาย ก.ย. 2026** รวม **ช่วง incident 29 ก.ย. 2026 (Hetzner บล็อก IP)** และช่วง 28 ก.ย.–1 ต.ค. ที่ journal ใหญ่ผิดปกติ · log แอป ener-scan ไม่อยู่ใน journal (docker json-file) จึงไม่หาย
- **ก่อน vacuum (บังคับ — แก้ตาม Codex):** (1) สำรองหลักฐานที่ตกลงเก็บเป็น export: `journalctl --since 2026-09-27 --until 2026-10-02 -o export > /root/backup-ops-20261002/journal-incident-20260927-1001.export` (ตรวจพื้นที่ว่างก่อน ≤3G; ไม่พอให้แบ่งช่วง) และบันทึกจำนวนรายการต้นทาง `journalctl --since … --until … -q | wc -l` (2) **แปลงกลับเป็นไฟล์ .journal** ด้วย `systemd-journal-remote` (export format เปิดด้วย `--file` ตรง ๆ ไม่ได้): `/usr/lib/systemd/systemd-journal-remote -o /root/backup-ops-20261002/journal-incident-20260927-1001.journal /root/backup-ops-20261002/journal-incident-20260927-1001.export` (ต้องมีแพ็กเกจ `systemd-journal-remote` — ตรวจ `dpkg -l | grep journal-remote` ก่อน ไม่มีต้องขออนุมัติติดตั้ง) (3) **ตรวจอ่านคืน (เกณฑ์ = เท่ากันเท่านั้น):** นับ record แบบ 1 record/บรรทัด: ต้นทาง `journalctl --since … --until … -o json -q | wc -l` เทียบกับ `journalctl --file=…1001.journal -o json -q | wc -l` **ต้องเท่ากัน** (ไม่ใช้ `-o short` เพราะ 1 รายการอาจมีหลายบรรทัด) และ `journalctl --file=… --since 2026-09-29 --until 2026-09-30 -u docker -o json -q | wc -l` > 0 (มีรายการช่วง incident จริง) — ไม่เท่ากัน/เป็น 0 = หยุด ไม่ vacuum (4) แล้วค่อยบีบ export ด้วย `zstd` เก็บคู่กับ .journal (5) บันทึก `journalctl --disk-usage` + รายชื่อไฟล์ก่อน/หลัง · **คืนประมาณ ~2.9G (ประมาณการ)**

## 3. F — btmp: หลักฐาน SSH ล้มเหลว ไม่ใช่ "ไม่มีผลกระทบ"
- ปัจจุบัน: `btmp` 184MB (1–19 ต.ค.) + `btmp.1` 440MB (ก.ย.) · logrotate.d/btmp = monthly, rotate 1, ไม่บีบอัด → รอบ 1 พ.ย. จะลบ btmp.1 ทิ้ง (หลักฐานเดือนก.ย. หายเองอยู่แล้ว) · failed logins **31,382 ครั้ง/24 ชม.** · fail2ban ติดตั้งแต่ **inactive**, ufw inactive, sshd `passwordauthentication yes` (root = without-password)
- **ข้อเสนอ F (แก้ตาม Codex):** แก้ `/etc/logrotate.d/btmp` → `monthly, rotate 6, compress, delaycompress, missingok, create 0660 root utmp` = เก็บ **6 รอบหมุนเวียน** (ปกติ = 6 เดือน แต่ถ้ามี force rotate เพิ่มจะสั้นกว่านั้น — ไม่รับประกัน 6 เดือน) · `compress` = **แทนที่ไฟล์เดิมด้วยไฟล์ .gz** (ไฟล์ดิบถูกลบหลังบีบ ไม่ใช่ "ไม่ลบไฟล์ใด") · เนื้อหาอ่านคืนด้วย `zcat btmp.2.gz > /tmp/b && lastb -f /tmp/b | head` ต้องตรวจก่อนปิดงาน
- **ขั้นตอน:** (1) read-only ก่อน: `logrotate -d /etc/logrotate.d/btmp` (debug ไม่เปลี่ยนระบบ) + บันทึก `ls -la --time-style=long-iso /var/log/btmp*` + `lastb -f /var/log/btmp.1 | wc -l` (2) แก้ config (3) ถ้ากบต้องการคืนพื้นที่ตอนนี้: `logrotate -f /etc/logrotate.d/btmp` 1 ครั้ง → คาด: btmp (184MB ต.ค.) → btmp.1 (ยังไม่บีบเพราะ delaycompress), btmp.1 (440MB ก.ย.) → btmp.2.gz (~45MB ประมาณการ) · **คืนประมาณ ~395MB (ประมาณการ ยืนยันจาก ls หลังทำ)** (4) รายงานรายการไฟล์ก่อน–หลัง + ผล `lastb` จากไฟล์บีบอัดว่าเนื้อหาหลักฐานเดือน ก.ย. ยังอ่านได้
- **ข้อเสนอ F2 (ลดต้นตอ — ความปลอดภัย):** เปิด `fail2ban` jail sshd (ban 1 ชม. หลัง 5 ครั้ง) และ/หรือ `PasswordAuthentication no` (เราเข้าด้วย key อยู่แล้ว — ต้องยืนยันว่ากบ/ทุกคนใช้ key) → ลด btmp/journal จาก sshd ~90% · **ต้องอนุมัติแยก** เพราะกระทบการเข้า SSH

- cron 04:00 ไทย: `ener-cleanup.sh` (`docker builder prune -f`, `docker image prune -f` = dangling เท่านั้น, `docker container prune -f`, ลบคลิป vdo เกิน 20 ไฟล์) + อีกบรรทัด `docker builder prune -af --filter until=72h` + `docker image prune -f`
- **image สำหรับ rollback (แก้ตาม Codex — ตรวจด้วย image ID):** Pro: **ไม่ได้บันทึก image ID ก่อน deploy** (15 ต.ค. และ 19 ต.ค.) → **ยังยืนยันไม่ได้ว่า image `eedec5b` ของ Pro เหลืออยู่** · staging: บันทึก ID ก่อน deploy ไว้ (`87cbf2c2478b` web, `7f2182dfdea3` worker-scan, `fe0bcd387c48` worker-maintenance, `bbfe50d39109` worker-delivery) → `docker image inspect` ทั้ง 4 = **not found** = image staging ก่อน deploy ถูกลบแล้วจริง · หลักฐานประกอบ: `docker images -a -f dangling=true` = 0 รายการ, cron 04:00 วันนี้ (ก่อน deploy) reclaim 0B — **สาเหตุ/เวลาที่ถูกลบยังไม่ยืนยัน** (cron คืน 0B ไม่พิสูจน์ว่าถูกลบระหว่าง deploy; ไม่มี docker events/log ยืนยัน) · Pro: **ไม่ยืนยัน** ทั้งการมีอยู่และสาเหตุ · ผล: rollback ตาม runbook (`deploy-pinned.sh pro eedec5b…`) = **build ใหม่จาก git** (~2–4 นาที; build cache ถูก prune ที่ 72 ชม.) ไม่ใช่สลับ image ทันที
- **ข้อเสนอ (แก้ตาม Codex):** ใน deploy-pinned ก่อน build: อ่าน **image ID ของคอนเทนเนอร์ที่กำลังรันจริง** (`docker inspect -f '{{.Image}}' <container>`) แล้ว `docker tag <imageId> ener-scan-pro-<svc>:rollback-<sha7เดิม>` ทั้ง 4 บริการ + บันทึก ID ลงไฟล์ `/root/ener-scan-pro/.last-images-<sha7>.txt` · **วิธีย้อนด้วย image นั้น (ไม่ build):** `deploy-pinned.sh` เพิ่มโหมด `--use-image-tag rollback-<sha7>` = checkout SHA เดิม (เพื่อให้ compose/healthcheck ตรง) แล้ว `docker compose up -d --no-build` โดย compose อ้าง image tag นั้น (ต้องปรับ compose ให้รับ `IMAGE_TAG` env) → สลับภายใน ~15 วิ · tag ป้องกันเฉพาะ **dangling prune** (`docker image prune -f`) — **ไม่ป้องกัน `prune -a`** และคอนเทนเนอร์ที่ไม่ได้ใช้ tag นั้นก็ยังถูก `prune -a` ลบได้ → cron ปัจจุบันไม่มี `-a` (ปลอดภัย) แต่ต้องห้ามเพิ่ม `-a` ในอนาคต · เก็บ rollback 1 ชุด (ลบชุดก่อนหน้าเมื่อ deploy ถัดไปผ่านตรวจ) · ต้นทุนพื้นที่ ≤ 4×1.15GB (layer ร่วมจริงน่าจะ ~1.5G วัดหลังทำ) · ต้องแก้สคริปต์ + compose (commit ใหม่) + อนุมัติ
- cron ไม่แตะ image ที่มี tag, log, journal, ollama → ไม่ช่วยเรื่องดิสก์ 85% ที่เป็นอยู่

## 5. ติดตามพื้นที่ว่างต่อเนื่อง (ข้อท้ายของ Codex)
- ตัวเลข "~40MB/วัน" ครอบเฉพาะ log legacy — journal จริง 1.4–2.9G/เดือน (50–100MB/วัน) และ build/pull image ใช้เป็นก้อน (deploy วันนี้ +8 images ×1.15GB แต่ layer ร่วม) → ต้องวัดจริง
- sysstat เก็บอยู่แล้วทุก 10 นาที แต่ `SADC_OPTIONS="-S DISK"` (ไม่มี FS) และ `HISTORY=7` · **ข้อเสนอ:** `SADC_OPTIONS="-S DISK,XDISK"` + `HISTORY=28` แล้ว restart sysstat → ดูย้อนหลังด้วย `sar -F -f /var/log/sysstat/saDD` (ต้องอนุมัติ: แก้ config + restart service เล็ก) · ทางเลือกไม่แตะ service: cron ทุกชั่วโมง `df -B1 / >> /root/storage/df-history.log`
- จนกว่าจะอนุมัติ: ตรวจ `df -h /` ด้วยมือทุกครั้งที่ทำงาน ops · ขณะนี้ 85% / ว่าง 12G (`sar -F` สด 15:50 ไทย: 84.91% ใช้, inode 17%)
