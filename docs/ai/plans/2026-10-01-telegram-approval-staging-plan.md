## 3. รายการทดสอบสังเคราะห์ — แยกสองความหมายให้ชัด
- **"คำขอถูก denied"** = ระบบปฏิเสธ *การกด* (ผู้กดไม่อยู่ในรายชื่อ / ผิดห้อง / ผิด secret / ปุ่มหมดอายุ / token ใช้แล้ว / รายการ stale) — รายการ `payments` **ไม่เปลี่ยนสถานะ** มีแต่ audit
- **"เจ้าหน้าที่ปฏิเสธสลิป"** (เปลี่ยน `payments.status` → `rejected` + แจ้งลูกค้า) — **ยังไม่มีใน Telegram handler** (รองรับแค่ `ap:` ขออนุมัติ และ `cf:` ยืนยันอนุมัติ; ปุ่มอื่น → "ปุ่มนี้ไม่รองรับ") · ทำได้ทางเว็บ admin เดิมเท่านั้น · ถ้าต้องการใน Telegram = งานใหม่ ต้องเสนอขอบเขตก่อน (ปุ่ม `rj:` + token แบบเดียวกับ cf + `rejectPayment` ผ่าน store เดิม + audit + ข้อความแจ้งลูกค้า) — **ไม่รวมในรอบนี้ ไม่รายงานว่าพร้อม**
**ก. มีอยู่แล้ว (ชี้หลักฐาน):** `scripts/ops/test-payment-approval-db.mjs` (RPC 061–063: เติมครั้งเดียว · 5 concurrent · audit rollback · retry · stale snapshot · outbox crash dedupe · PUBLIC denied) + `tests/telegramSlipApproval.behavior.test.js` (denied ทุกแบบ · stale · เว็บอนุมัติก่อน · DB/แจ้ง/audit/Telegram ล้ม · ไม่มี GET · ไม่รั่ว token) + `paymentApprovalHardening.test.js` — ใน gate ✅
**ข. ใหม่ (1 ต.ค.) `scripts/ops/test-telegram-approval-integration.mjs`** — router+handler+RPC จริงใน Postgres (schema staging) + PostgREST · Telegram API ตัดจบในเครื่อง (บันทึก method/body) · network guard · config ค่าทดสอบ: flag ปิด=404 · secret ผิด=401 ไม่แตะ DB · อัปเดตไม่ใช่ปุ่ม=ignored · **regression: callback JSON ต้องถูก parse** · แจ้งสลิป → ปุ่ม `ap:` + audit · denied (user/chat) + audit, รายการไม่เปลี่ยน · ขั้น 1 ออก `cf:` ไม่เปลี่ยนสถานะ · ขั้น 2 → paid + grant 1 + audit `approve_confirmed:ok` 2 แถวโดยดีไซน์ (RPC ใน transaction เดียวกับ grant + handler หลังแจ้งลูกค้า) + ข้อความลูกค้า **ถูกกักใน `outbound_messages` (queued) ไม่ส่ง LINE** · กดซ้ำ/ap ซ้ำ=stale ไม่เติมซ้ำ · sweep ไม่สร้างแถวซ้ำ · 3 concurrent → grant 1 · หมดอายุ/ยอดเปลี่ยน → ไม่เติม · `rj:` → ไม่รองรับ (ช่องว่างฟีเจอร์) · blocked=0 ไม่มี token/secret ใน log
**ค. ทดสอบสด (หลัง 2a+2b และเลือกวิธีกักข้อความในข้อ 4 แล้ว — อนุมัติแยก):** รายการ `pending_verify` สังเคราะห์ (UID สังเคราะห์ `Uittg…` ไม่ใช่บัญชีจริง) → ข้อความเข้า Telegram ห้องทดสอบ → ผู้อนุมัติกดใน Telegram จริง (ไม่ login เว็บ · ระบบตรวจ numeric id + chat + secret ทุกครั้ง) → ตรวจ grant 1 / audit / token ใช้แล้ว / กดซ้ำ stale / คนนอกกด denied · outbound ของรายการต้อง **ไม่ถูกส่ง** (ตามวิธีข้อ 4) · สถานะหลังทำ: **อนุมัติผ่าน Telegram = automated PASS / live NOT TESTED จนกว่าจะทำ ค. · ปฏิเสธสลิปผ่าน Telegram = ยังไม่มี**

## 4. กันข้อความแจ้งผลหลุดไปหาลูกค้าจริง — **ไม่ใช้ ban gate** (Codex: `wrapClientWithBanGuard` fail-open เมื่อตรวจแบนล้ม → รับประกันไม่ได้ · ไม่เปลี่ยนกติกาแบนทั้งระบบเพื่อเทสต์) · ไม่ใช้ UID ปลอมหวัง LINE ตอบ 400
- **ระบบแยก (ทำแล้ว):** harness ข — ข้อความ "เติมสิทธิ์แล้ว" ลง `outbound_messages` (`approve_notify`, `queued`) และไม่มี delivery worker + network guard บล็อกทุกการออกนอก → อ่านตรวจจากแถว ส่งออกไม่ได้จริง
- **ทดสอบสด — เสนอ 2 วิธี ขออนุมัติเลือกก่อนทำ:**
  - **วิธี A (Codex เลือก 1 ต.ค. — ชุดขออนุมัติ: `docs/ai/plans/2026-10-01-telegram-live-isolated-approval.md`, โหมด `--live` ของ harness, SHA `ec30253`): ระบบทดสอบแยกรับ callback จาก Telegram จริง แต่ไม่มี LINE transport** — รัน stack ของ harness (app + Postgres/PostgREST ใช้แล้วทิ้ง, config Telegram ทดสอบ, network guard) บนเซิร์ฟเวอร์ที่ loopback port แล้วเพิ่ม `location = /telegram/webhook-it { proxy_pass http://127.0.0.1:<port>/telegram/webhook; }` ใน server `test.my-ener.uk` ชั่วคราว → `setWebhook` bot ใหม่ชี้ URL นี้ → ผู้อนุมัติกดปุ่มจริงใน Telegram → ตรวจ grant/audit ใน DB ทดสอบ · **ไม่มีทางถึง LINE** (ไม่มี delivery worker, guard บล็อก) · ไม่แตะ DB/คิว staging เลย · ข้อแลก: ต้องแก้ nginx ที่แชร์กับ Pro (อนุมัติแยก — รวมรอบเดียวกับ masking ได้) และถอด location หลังจบ · ไม่ได้ทดสอบ image/compose ของ staging จริง
  - **วิธี B (ไม่ทำ — Codex เลือก A): หยุด `worker-delivery` ของ staging ชั่วคราว** ระหว่างทดสอบ (ใช้ image/DB staging จริง) — ผลกระทบ: outbound ทุกชนิดของ staging ค้างคิวตลอดช่วง (staging มี 5 บัญชีทดสอบ ไม่มีลูกค้าจริง; สแกน/ตอบของกบบน staging จะช้าจนเปิดกลับ) · ขั้นตอน: (1) ก่อนหยุด ตรวจคิวว่าง `select count(*) from outbound_messages where status in ('queued','sending','retry_wait')` = 0 (ไม่ว่าง = รอ/หยุดแผน) (2) `docker compose stop worker-delivery` (ไม่ลบ container, image เดิม) (3) ทำ ค. (4) **cleanup ข้อ 4.1 ให้ครบก่อน** (5) `docker compose start worker-delivery` แล้วเฝ้า log 10 นาที ว่าไม่มี event ส่งของ UID สังเคราะห์
- **4.1 Cleanup หลังทดสอบสด (วิธี B) — ครอบ intent/sweep/outbound ค้าง · เก็บ grant/audit/payments ไว้ · ไม่ลบ UID ไม่ปลดแบนใคร:**
  1. ปิดทาง sweep: ทุก payment สังเคราะห์ที่อนุมัติแล้ว → `select mark_payment_grant_notified('<pid>')` (RPC เดิม ต้องมีแถว outbound เป็นหลักฐานจึงยอม stamp) → `payment_entitlement_grants.notified_at` ไม่ null → `list_payment_grants_pending_notify` ไม่หยิบอีก (ตรวจ `select count(*) from payment_entitlement_grants g join payments p on p.id=g.payment_id where p.line_user_id like 'Uittg%' and g.notified_at is null` = 0)
  2. ปิดทาง delivery: แถว outbound ของ UID สังเคราะห์ที่ยัง active → `update outbound_messages set status='dead', last_error_code='it_synthetic_quarantine', next_retry_at=null where line_user_id like 'Uittg%' and status in ('queued','sending','retry_wait')` (`dead` = สถานะ terminal ที่ schema อนุญาต ไม่มี retry; เป็นการจัดการข้อมูลสังเคราะห์ ไม่แก้โค้ด/ไม่เพิ่มทางข้ามสิทธิ์) · ตรวจ `select count(*) from outbound_messages where line_user_id like 'Uittg%' and status in ('queued','sending','retry_wait')` = 0
  3. ปิดทาง enqueue ซ้ำ: `enqueueApproveNotify` dedup เฉพาะแถว active — หลังข้อ 1 ไม่มีผู้เรียกใหม่ (sweep ไม่หยิบ, handler ไม่ถูกเรียกซ้ำเพราะ token ใช้แล้ว/paid) · ถ้ามีการกด `ap:` ซ้ำ = stale ไม่ enqueue
  4. เก็บหลักฐาน: ไม่ลบ `payments`/`payment_entitlement_grants`/`payment_approval_audit`/`telegram_approval_tokens`/`app_users` ของ UID สังเคราะห์ (บันทึก id ไว้ในรายงาน) · ไม่แตะแถวของบัญชีอื่น
  5. จากนั้นค่อย `start worker-delivery` · เฝ้า log: ไม่มี `OUTBOUND_*`/`LINE_TRANSPORT_*` ของ UID สังเคราะห์
- ห้ามสร้าง `pending_verify` ให้บัญชีจริง/บัญชีกบ (ถ้ากบต้องการ end-to-end ด้วยบัญชีตัวเอง = เติมสิทธิ์จริงบน staging ต้องขออนุมัติผลกระทบ+บันทึกยอดก่อน/หลัง)
- ข้อความเข้า Telegram ไปเฉพาะห้องของ bot ใหม่ · ก่อน `setWebhook`: `getWebhookInfo` ว่าง · `secret_token` = `TELEGRAM_WEBHOOK_SECRET` · `allowed_updates=["callback_query"]` · URL ของ staging/ระบบทดสอบเท่านั้น ไม่ใช่ scan.my-ener.uk
